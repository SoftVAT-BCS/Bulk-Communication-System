Internal fields: `id uuid` generated by core `gen_random_uuid()`, `portal_key text`
required from trusted authorization (never inferred from CSV), `created_at` and
`updated_at timestamptz`. Unique `(portal_key, target_id)` is the import identity.
IDs remain case-sensitive in SQL; the fixture validator conservatively rejects
case-only duplicates for review. Email is deliberately not unique: shared contact
addresses may be legitimate; this fixture requires duplicates to be reviewed.
The trigger prevents identity/portal/created timestamp mutation and maintains updated_at.
Importer must omit all generated/timestamp fields and use a column-level allowlist.

Indexes: portal + group/category, portal + status, portal + lower(email), portal +
lower(name), plus portal/target unique key. Lowercase text_pattern_ops supports
appropriate prefix queries; these indexes do not promise arbitrary substring search.
No extension installation or speculative indexes. Revisit search plans with real sizes.
Step 3B-2 removes the global demo group/category tuple CHECK. Required fields instead
use named nonblank CHECKs (`~ '[^[:space:]]'`), including rejection of ordinary spaces,
tabs and newlines alone. Unicode whitespace classification must be rehearsed under the
target collation; future API mapping must independently reject Unicode whitespace-only
labels and control characters. Nonblank SQL checks do not establish a valid relationship.
The unchanged checksum-pinned validator still enforces the exact demo vocabulary.
Future adapters validate portal-specific group/category relationships; tenant-scoped
reference tables may later be justified, but none are added here.

## Migration and execution gates

Migration: [0001_bcs_demo_recipients.sql](../../database/migrations/0001_bcs_demo_recipients.sql).
It has **not been executed or database-parser validated**. It creates only the BCS
schema, one table, indexes and one update trigger/function, in one transaction.
It deliberately uses CREATE without IF NOT EXISTS: any existing schema, even a
compatible one, aborts. A migration runner must record/check applied checksum/version
outside this migration; never rerun or repair an existing schema automatically.

Before separately authorized execution:

1. Approve exact database identity and supported PostgreSQL version; verify core UUID,
   PL/pgSQL, ACL and RLS features on that version. No live server version was queried.
2. Take a restorable backup/PITR checkpoint and test restore to an isolated database.
   Inventory existing BCS objects, default ACLs, role memberships, exposed schemas,
   event triggers and extensions. Stop on name conflicts or unexpected DDL side effects.
3. DBA pre-provisions `bcs_demo_owner` NOLOGIN NOSUPERUSER NOBYPASSRLS, without CRM
   memberships. Migration identity needs permission to SET ROLE to it, and the owner
   needs CREATE on the approved database. This migration creates no global roles.
4. Use a reviewed client with stop-on-error, UTF-8 client encoding and transaction
   support; credentials come from a private secret manager, never command-line literals.
   Rehearse exact migration on a disposable authorized local database first.
5. Verify columns, constraints, indexes, trigger, ownership, ACLs, RLS and default-deny
   behavior. Any failed transaction must be rolled back; do not continue statements.

No destructive down migration is supplied. Before commit, transaction rollback
removes attempted DDL. After deployment, use reviewed forward corrections or restore
the tested backup into a separate environment; do not automatically drop/truncate
recipient data or restore over shared CRM data. Preserve import receipts and hashes
outside source control, without recipient values.

## Security and isolation proposal

The migration revokes PUBLIC object access, enables **and forces** RLS and installs
**no policies and no runtime grants**. The result intentionally cannot serve or import
recipients until a separately reviewed access migration. Unexpected inherited default
ACL grants abort the transaction. Role memberships and platform owner privileges
still require DBA review: schema separation alone is not tenant isolation.

Prefer dedicated non-owner, non-superuser, non-BYPASSRLS backend identities per portal
for this initial import. A later approved policy should target each specific role and
literal authorized portal, with SELECT/UPDATE USING and INSERT/UPDATE WITH CHECK.
Reader receives schema USAGE and SELECT only; importer receives SELECT and column-
scoped INSERT/UPDATE, no DELETE/TRUNCATE/DDL or unrestricted role switching. Application
connections must never use the migration owner or a Supabase service-role credential.
Owner FORCE RLS does not constrain superusers/BYPASSRLS roles. A client-controlled
portal key or custom session setting alone is not an authentication boundary.
Shared-pool identity mapping, membership rules and policy implementation remain open.

Private backend-only TLS connections with certificate validation, restricted network
access, secret rotation and bounded pools are required. Authorize portal on every
operation (including counts/search/export); reject requested keys outside that scope.
No database connection strings or service keys in React, NEXT_PUBLIC variables,
bundles, logs or demo storage. Keep BCS out of Supabase exposed schemas; grant no
access to anon/authenticated/service_role and add no exposed views/RPC wrappers.
Do not alter shared Data API configuration used by CRM; disabling the whole API is
only an option after a separate impact review. Verify effective roles, REST/GraphQL
and Realtime exposure in an authorized environment before deployment.

Required later negative tests: cross-portal reads/counts/updates/inserts/upserts,
forged/missing scope, anonymous/API access, attempted portal reassignment, role
membership escalation and pooled-connection reuse. Active is not permission to send;
consent and suppression must be independently enforced in future sending workflows.

The standard-library validator is pinned to this source SHA-256 and fails on changed
input. It emits only aggregates. Optional `--utf8-output` takes an explicit new path
and opens exclusively (`xb`); it never overwrites. Use only an owner-approved private
local destination outside version control. No converted copy is needed for review.
Conversion is strict CP1252 to UTF-8 without BOM, preserving tab delimiter, cells and
line endings. Do not open/resave with spreadsheet numeric inference or use replacement
characters. Independently verify output hash above and all 240 parsed row values.

After deployment and portal-policy approval, implement/review a parameterized importer:

1. Verify source hash, 17 ordered headers, widths, 240 rows and all validator rules.
   Keep identifiers as strings; only exact empty optional cells become NULL. Reject
   unexpected whitespace rather than silently trimming identities. If future populated
   dates/contact fields appear, stop for a new source and format review.
2. Resolve the authorized portal from backend identity; it is absent from this file.
   Reject duplicate target IDs and casefolded emails within the batch. Do not log rows.
3. Start one transaction under the approved portal importer role. Serialize imports
   for that portal (reviewed job lock), inspect existing matching identities and compare
   every mapped value with NULL-safe equality. Require expected pre-import counts.
4. Default repeat rule: insert missing `(portal_key,target_id)`; identical existing
   rows are no-ops; any changed existing row aborts the whole batch for review. Never
   blindly overwrite Bounced/Unsubscribed with Active. Prefer parameterized INSERT
   with explicit columns and conflict handling followed by a complete equality check;
   concurrent mismatches must fail, not become silently skipped conflicts.
5. For an empty approved demo portal expect inserted=240, unchanged=0, changed=0,
   total=240. Exact repeat expects inserted=0, unchanged=240, changed=0, total=240.
   Check all four status totals and group/category totals before commit. Unexpected
   preexisting rows, conflicts, count changes or validation errors roll back everything.
6. Any future overwrite/upsert mode needs explicit change approval, before-image
   recovery and status/consent authority rules. Stable conflict key remains portal+target;
   email/name must never select a recipient identity. No deletes of absent source rows.

Do not COPY directly into the RLS table: use parameterized INSERTs. No importer DB
driver, connection routine or executable import command is introduced in this task.
